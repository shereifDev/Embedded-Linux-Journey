الآن عرفنا أنواع ملفات ELF التي:

  • النوع الأول — Relocatable: ملفات .o قابلة للدمج لكنها غير قابلة للتشغيل مباشرة لأنها تحتوي على رموز غير معرفة (Undefined Symbols) وعناوين ناقصة.
  • النوع الثاني — Executable: الملف النهائي القابل للتشغيل مباشرة.
📘
أنواع ELF المعروفة
معيار ELF يمتلك 4 أنواع، لكن في هذا الدرس تم الكشف عن النوع الثالث الأساسي من ملفات ELF (مع التنويه بأن النوع الرابع غالبا Core Dump — كأنظمة مهدرة — وجهلها كمهندس لن يعيقك ويقع خارج نطاق الدورة).
SECTION 10.2
ELF — الملفات من النوع الثالث (Shared Object)
📌
ما هو النوع الثالث؟

الاسم: ملف الكائن المشترك (Shared Object / Shared Library)

الامتداد: .so (في لينكس) ويقابله .dll في ویندوز.

الوظيفة: ملف ELF يحتوي على كود برمجي مجمع ومبني (مثل دالة printf داخل مكتبة C) ومصمم ليتم تحميله في الذاكرة ليتم استخدامه قبل عدة برامج في نفس الوقت (Runtime).

الوصف المقابل القيمة
اسم النوع Shared Object / Shared Library —
امتداد الملف في لينكس .so —
المقابل في ویندوز .dll —
المحتوى كود برمجي مجمع ومبني (مثل دالة printf داخل مكتبة C) —
طريقة الاستخدام يُحمَّل في الذاكرة ويُستخدم قبل عدة برامج في نفس الوقت Runtime

SECTION 10.3
التفصيل المعماري: كيف يعمل اللينكر (Linker — ld)؟

سابقا عرفنا أن اللينكر يحل مشكلة الرموز المفقودة، لكن كيف يفعل ذلك هندسيًا؟

1
Section Merging — دمج الأقسام
اللينكر يأخذ عدة ملفات .o ويفتح كل ملف ويجمع كل أقسام (text) مع بعضها، ويقوم بنفس الشيء مع data و .bss لعمل قسم text واحد كبير للملف النهائي.
2
Address Binding — تحديد العناوين
اللينكر يعطي لكل دالة وكل متير عنوانا ثابتا افتراضيا وحقيقيا في الملف النهائي، بينما تكون العناوين في ملف .o نسبية أو وهمية.
3
Symbol Resolution — حل الرموز
اللينكر يربط النداءات (Calls) في الكود بالعناوين الحقيقية التي تم حسابها توًا.

SECTION 10.4
المعركة الكبرى: الثابت الربط (Static) مقابل الدینامیكي (Dynamic)

هنا تكمن زبدة الدرس — الفرق بين المبرمج العادي ومهندس الأنظمة المدمجة (Embedded Systems Engineer) الذي يُحاسب على كل ميجابایت من الذاكرة.

Static Linking — الثابت الربط
📌
ما هو Static Linking؟

الآلية: اللينكر ld يقوم بنسخ الكود البرمجي الخاص بالدالة من مكتبة ثابتة (مثلاً .a) ولصقه فعلیا وحرفیا داخل الملف التنفيذي النهائي.

الميزة (Portability): يعمل البرنامج بشكل مستقل تماماً لا يحتاج لأي مكتبات خارجية على نظام العمیل لتشغیلھ.

العیب: يصبح حجم الملف جداً ضخماً — من الأھم ذلك: إذا قمنا بتشغیل 5 برامج تستخدم نفس المكتبة سيكون هناك إھارا جداً يسبب تكرار تحمیل نفس الكود 5 مرات في الذاكرة العشوائیة (RAM) — كارثیا لموارد النظام المدمج!

Dynamic Linking — الدینامیكي الربط
📌
ما هو Dynamic Linking؟

الآلية: اللينكر ld لا ينسخ الكود بل يترك رابطا (Reference) في الملف التنفيذي يخبر النظام: "هذا البرنامج يحتاج الفلانیة الدالة من الفلانیة المشتركة المكتبة للعمل".

الميزة: يصبح حجم التنفيذي الملف جداً صغیراً — تستضیف الذاكرة (RAM) نسخة واحدة فقط من المكتبة (مثل libc.so) وتتشاركھا كل البرامج (Shared Memory).

العیب: إذا تم حذف المكتبة من النظام أو تغیر مسارها سيتعطل البرنامج ولن یشتغل.

المعيار Static Linking Dynamic Linking
الآلية اللينكر ld ينسخ الكود ويصقه فعلیا داخل الملف التنفيذي اللينكر ld يترك رابطا (Reference) فقط في الملف التنفيذي
حجم الملف التنفيذي ضخم جداً صغیر جداً
الاستقلالية (Portability) يعمل بشكل مستقل تماماً بدون مكتبات خارجية يعتمد على وجود المكتبات المشتركة في النظام
استهلاك RAM إھارا — تكرار تحمیل نفس الكود عدة مرات نسخة واحدة من المكتبة تتشاركها كل البرامج (Shared Memory)
ملف المكتبة .a (Static Library) .so (Shared Object)
ملاءمة الأنظمة المدمجة كارثیا لموارد النظام المدمج مثالي للأنظمة المدمجة ذات الموارد المحدودة
نقطة الضعف استھلاك مساحة وتخزین إذا حُذفت المكتبة أو تغیر مسارها سيتعطل البرنامج

Static Linking
Executable A (50MB)
├─ main() code
├─ printf() copy
└─ malloc() copy
Executable B (50MB)
├─ main() code
├─ printf() copy
└─ malloc() copy
Total RAM: 100MB ⚠
Dynamic Linking
Executable A (5KB)
├─ main() code
└─ → ref to libc.so
Executable B (5KB)
├─ main() code
└─ → ref to libc.so
libc.so (Shared) — 1 copy
printf() • malloc() • ...
Total RAM: ~10KB + lib ✅

SECTION 10.5
اللودر (The Loader / Dynamic Linker)

إذا كان اللینكر العادي ld يترك "علامة" فقط للربط الدینامیكي ولا يجلب الكود، فمن يقوم بالربط الفعلي عند تشغیل البرنامج؟

🧠
البطل الخفي: اللودر
يتدخل هنا اللودر الخفي — وهو المكون الذي يُنجز الربط الفعلي وقت التشغيل على اللوحة المدمجة (Target) وليس على جهازك القوي (Host).
كيف يعمل اللودر؟ ⚙
1
قراءة ترویسة ELF
عندما تطلب تشغیل برنامج من الشل، الكیرنل (Kernel) يقرأ ترویسة الملف ELF الخاص بھ.
2
اكتشاف الاعتماديات الدینامیكیة
الكیرنل يكتشف أن ھذا البرنامج يحتاج كلیا لربط دینامیكي بالمكتبات.
3
مناداة اللودر
الكیرنل يقوم بمناداة اللودر (وھو تطبيق/مكتبة خاصة عادة اسمھ ld-linux.so في أنظمة أوبونتو أو ld-uClibc.so في الأنظمة المدمجة).
4
البحث عن المكتبات المشتركة
اللودر يبحث في مجلدات النظام القیاسیة (مثل lib/ و usr/lib/) عن المكتبات المشتركة المطلوبة.
5
تحميل المكتبات في RAM و Resolve
يضع المكتبات في الذاكرة العشوائیة (RAM) ثم يقوم بعملیة Resolve أخیرة (في وقت التشغیل) ليربط البرنامج بعناوین الدوال داخل المكتبة.
6
تسیم التحكم للبرنامج
أخیراً، اللودر يسلم التحكم للبرنامج لیبدأ العمل.

مراجعة سريعة — Quick Review
Main Concepts — المفاهیم الأساسیة
  • مراحل البناء الأربع: Preprocessing → Compilation → Assembly → Linking
  • أنواع ملفات ELF: Relocatable (.o)، Executable، Shared Object (.so)، Core Dump
  • النوع الثالث من ELF هو Shared Object — مكتبة مشتركة تُحمَّل في RAM وقت التشغیل
  • اللینكر ld يعمل بثلاث خطوات: Section Merging، Address Binding، Symbol Resolution
  • Static Linking ينسخ الكود حرفیاً داخل الملف التنفيذي — حجم ضخم واستھلاك مفرط لـ RAM
  • Dynamic Linking يترك رابطاً (Reference) فقط — حجم صغیر ومشاركة مكتبة واحدة في RAM
  • اللودر ld-linux.so / ld-uClibc.so یُنجز الربط الفعلي وقت التشغیل على Target
  • اللینكر يعمل على Host في Compile-time، واللودر يعمل على Target في Run-time
Important Definitions — تعریفات مهمة
  • Shared Object (.so): ملف ELF يحتوي على كود برمجي مجمع مصمم ليتم تحميله في الذاكرة ومشاركته بين عدة برامج
  • Static Linking: نسخ الكود من مكتبة .a ولصقه فعلیاً داخل الملف التنفيذي
  • Dynamic Linking: ترك رابط (Reference) في الملف التنفيذي يشیر إلى مكتبة .so خارجية
  • Section Merging: جمع أقسام text و data و .bss من عدة ملفات .o في قسم واحد
  • Address Binding: تحويل العناوين النسبية في .o إلى عناوين ثابتة افتراضية وحقيقية
  • Symbol Resolution: ربط النداءات (Calls) بالعناوين الحقيقية المحسوبة
  • The Loader: مكتبة خاصة يُناديها الكیرنل لتحميل .so وربط الرموز فعلیاً في RAM
  • Resolve: العملية الأخيرة التي يُنجزها اللودر — ربط عناوین الدوال داخل المكتبة بالبرنامج
Common Mistakes — أخطاء شائعة
  • الخلط بين ld (اللینكر الذي يصنع الملف) واللودر (الذي يقرأ الملف ويربطه في الذاكرة)
  • ظن أن غیاب ملف .so يُسبب خطأ أثناء البناء — في الحقيقة الخطأ یظهر عند تشغیل البرنامج على اللوحة
  • اعتبار Static Linking دائماً أفضل لأنه "مستقل" — ناسياً أنه كارثي لموارد الأنظمة المدمجة
  • نسيان أن اللودر نفسه مكتبة .so يجب أن توجد على النظام المستهدف
Interview Notes — ملاحظات المقابلات
  • "ما الفرق بين Static و Dynamic Linking؟" — أجب من منظور Embedded: RAM و Storage
  • "كيف يعمل اللینكر؟" — اشرح الثلاث خطوات: Merging → Binding → Resolution
  • "ماذا یحدث عند تنفیذ برنامج Dynamically Linked؟" — اشرح سلسلة اللودر الست
  • "لماذا .so وليس .o للمكتبات؟" — لأن .o غير قابل للتشغیل ويحتوي رموز غير معرفة
  • "ما الفرق بين ld و ld-linux.so؟" — Compile-time على Host مقابل Run-time على Target
Memory Tips — حیل للحفظ
  • ld = Linker = Compile-time = Host — الحرف الأول "L" يشیر للینكر الذي يعمل مبكراً على جهازك
  • ld-linux.so = Loader = Run-time = Target وجود ".so" یذكرك أنه یعمل على اللوحة المدمجة
  • Static = ضخم = كارثة RAM — تذكر: كل برنامج یحمل نسخته الخاصة = تضاعف
  • Dynamic = صغیر = مشاركة = RAM واحدة — تذكر: libc.so نسخة واحدة تتشاركها الكل
  • ELF Types: .o = ناقص، Executable = كامل، .so = مشترك، Core Dump = مهدر
Exam Tips — نصائح الامتحان
  • ركز على الفرق بين أنواع ELF الأربعة وأمثلة كل نوع
  • احفظ خطوات اللینكر الثلاث بالترتیب: Section Merging → Address Binding → Symbol Resolution
  • كن مستعداً لمقارنة Static vs Dynamic من عدة زوایا: الحجم، RAM، الاستقلالية، الأنظمة المدمجة
  • افهم تسلسل عمل اللودر بالترتیب — أي خطوة خاطئة تدل على عدم فهم العملية
  • تمييز ld-linux.so (أوبونتو) عن ld-uClibc.so (الأنظمة المدمجة) یظهر فهمك لبيئات Embedded
